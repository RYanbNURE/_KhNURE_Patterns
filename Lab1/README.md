# Лабораторна робота № 1
## Розподіл відповідальностей за GRASP

Це навчальний сценарій для адаптації до вимог конкретного курсу, а не офіційна програма або система оцінювання KHNURE. Запропонований нижче розподіл балів також є лише прикладом для погодження з викладачем.

### Мета роботи

Навчитися аргументовано призначати обов'язки об'єктам у системі резервування обладнання. GRASP у цій роботі розглядається як набір принципів призначення відповідальностей: він пов'язаний із SOLID і GoF, але не замінює їх і не є каталогом шаблонів.

Після виконання роботи студент має вміти пояснити дев'ять принципів GRASP і п'ять принципів SOLID, аргументовано перерозподіляти обов'язки між об'єктами, перевіряти поведінку тестами та оцінювати вплив рішень на зчеплення й зв'язність компонентів.

### Програмне забезпечення

- Python 3.9 або новіший;
- `pytest` для запуску тестів;
- базове розуміння класів, методів, списків і словників.

Зовнішні runtime-бібліотеки не потрібні. Версію Python і залежність для тестування можна перевірити командами `python --version` та `python -m pytest --version`.

### Структура проєкту

- `main.py` — демонстраційний сценарій резервування через Controller.
- `student_template.py` — шаблон із послідовними TODO для рефакторингу й політики тривалості бронювання.
- `solution.py` — окрема еталонна реалізація для самоперевірки.
- `tests/conftest.py` — спільні тестові дані й pytest-фікстури.
- `tests/test_implementation.py` — еталонні тести `solution.py`.
- `tests/test_template.py` — рання перевірка реалізації TODO 1.
- `tests/test_student_implementation.py` — заготовки тестів, які студент має завершити.
- `requirements.txt` — runtime-залежностей немає.
- `requirements-dev.txt` — pytest для розробки та тестування.
- `.gitignore` — ігнорує віртуальне середовище й кеші Python/pytest.

### Підготовка та запуск

Відкрийте у VS Code кореневу папку проєкту та створіть віртуальне середовище в PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
```

Перевірте, що використовується Python із віртуального середовища, і запустіть демонстрацію:

```powershell
.\.venv\Scripts\python.exe --version
.\.venv\Scripts\python.exe main.py
.\.venv\Scripts\python.exe -m pytest --collect-only -q
```

У VS Code виберіть `.venv` через **Ctrl+Shift+P → Python: Select Interpreter**. Надалі запускайте команди тим самим інтерпретатором. Для тестування скопіюйте шаблон:

```powershell
Copy-Item student_template.py student_implementation.py
```

### Перевірка тестами

Еталонні тести мають проходити незалежно від роботи студента:

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_implementation.py -v
```

До створення `student_implementation.py` файли `tests/test_template.py` і `tests/test_student_implementation.py` пропускаються через `pytest.importorskip`. Після копіювання шаблону ранній тест перевіряє TODO 1, а заготовки студентських тестів навмисно падають із `TODO`, доки студент не додасть виклики та assertions.

Після виконання TODO 1 запустіть ранню перевірку, потім студентський і повний набори:

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_template.py -v
.\.venv\Scripts\python.exe -m pytest tests/test_student_implementation.py -v
.\.venv\Scripts\python.exe -m pytest -v
```

Перед завершенням повний запуск має пройти без помилок і пропущених студентських тестів.

### Короткі теоретичні відомості

GRASP допомагає визначити, кому доручити відповідальність; SOLID — оцінити межі та залежності; KISS — уникати зайвої складності; DRY — не дублювати знання; YAGNI — не реалізовувати непідтверджені вимоги; Закон Деметри — обмежувати знання об'єкта про внутрішні ланцюжки інших об'єктів. Це пов'язані, але не взаємозамінні принципи.

| Принцип | Суть | Запитання до сценарію резервування |
|---|---|---|
| **Information Expert** (Інформаційний експерт) | Призначайте обов'язок об'єкту, який має потрібні для нього дані. | Який об'єкт має дані інтервалу, щоб визначити його перетин з іншим? |
| **Creator** (Творець) | Кандидатом на створення є об'єкт, який містить, використовує або має дані для нового об'єкта. | Хто має створити `Reservation`, призначити ID і додати його до колекції? |
| **Controller** (Контролер) | Не-UI-об'єкт приймає системну подію та делегує роботу відповідним об'єктам. | Хто обробляє запит на створення бронювання і чи делегує він бізнес-правила? |
| **Low Coupling** (Низьке зчеплення) | Зменшуйте зайві залежності між компонентами. | Які частини доведеться змінити при зміні правила конфлікту або способу зберігання? |
| **High Cohesion** (Висока зв'язність) | Зосереджуйте в компоненті невелику групу тісно пов'язаних обов'язків. | Чи зосереджує `Reservation` поведінку інтервалу, а `ReservationService` — сценарій бронювання? |
| **Polymorphism** (Поліморфізм) | Для змінної поведінки за типом розгляньте поліморфні реалізації замість умов. | Чи виправдані різні правила, якщо типи обладнання матимуть різну максимальну тривалість бронювання? |
| **Pure Fabrication** (Чиста вигадка) | Створіть допоміжний об'єкт, якщо це покращує зчеплення або зменшує залежності. | Чи варто винести з предметної логіки звіти або роботу зі сховищем? |
| **Indirection** (Посередництво) | Додайте посередника, щоб розділити компоненти, які інакше залежали б напряму. | Який компонент міг би ізолювати правила від сховища чи сповіщень? |
| **Protected Variations** (Захист від змін) | Стабілізуйте межу навколо очікуваного джерела змін. | Де провести межу, якщо з'являться різні сховища або правила доступності? |

Сценарій напіввідкритих інтервалів `[початок, кінець)` означає, що бронювання 10:00–11:00 не конфліктує з бронюванням 11:00–12:00. Polymorphism, Pure Fabrication, Indirection і Protected Variations не потрібно додавати штучно: достатньо пояснити, за якої вимоги вони були б виправдані.

У `solution.py` `Reservation` відповідає за знання про власний інтервал (Information Expert), `ReservationService` перевіряє правила, створює та зберігає бронювання (Creator), а `ReservationController` делегує системний запит (Controller). Цей варіант є прикладом для аналізу, а не обов'язковою структурою студентської реалізації.

#### П'ять принципів SOLID у цьому сценарії

GRASP допомагає визначити, кому доручити відповідальність; SOLID допомагає оцінити стійкість меж компонентів і залежностей. Не потрібно перетворювати кожен принцип на окремий клас.

| Принцип | Зв'язок із проєктом | Практичне застосування |
|---|---|---|
| **SRP** (Single Responsibility Principle) | `Reservation` відповідає за поведінку свого інтервалу, `ReservationService` — за сценарій бронювання, `ReservationController` — за приймання та делегування системного запиту. | Визначте основні причини для змін кожного компонента; за потреби запропонуйте мінімальний рефакторинг. |
| **OCP** (Open/Closed Principle) | Базова реалізація не має змінних правил тривалості, тому окрема ієрархія політик поки не потрібна. | Реалізуйте політику тривалості як окрему реалізацію без змін у `ReservationService`. |
| **LSP** (Liskov Substitution Principle) | Альтернативні політики мають зберігати спільний контракт і не ламати очікування клієнта. | Перевірте реалізації контрактними тестами: коректні запити приймаються, порушення правил дають передбачувану помилку. |
| **ISP** (Interface Segregation Principle) | `ReservationServicePort` містить лише потрібну Controller операцію `reserve`. | Передайте Controller тестову залежність без `list_reservations` та переконайтеся, що запит обробляється. |
| **DIP** (Dependency Inversion Principle) | `ReservationController` залежить від `ReservationServicePort`, а не від конкретного `ReservationService`. | Перевірте, що Controller працює з будь-яким об'єктом, який задовольняє вузький контракт. |

SRP, DIP та ISP відпрацьовуються на базовому сценарії. OCP і LSP є обов'язковими й закріплюються через ін'єкцію політики тривалості та контрактні тести.

#### Обов'язкові порушення та способи їх виправлення

Наведені нижче 18 випадків є обов'язковими навчальними варіантами, а не дефектами еталонного `solution.py`. Опрацьовуйте їх по одному у власній копії: зафіксуйте порушення та його наслідок, відтворіть його ізольованою зміною, додайте перевірку поведінки або контракту, виправте та переконайтеся, що поведінка збережена. Не залишайте навмисні порушення у фінальній реалізації. Для архітектурних принципів, які не перевіряються поведінковим тестом, зафіксуйте класи й залежності до та після виправлення у таблиці звіту.

| Принцип | Можливе порушення | Завдання на виправлення |
|---|---|---|
| **Information Expert** | `ReservationService` сам читає `starts_at` і `ends_at` кожного бронювання та повторює формулу перетину. | Перенесіть перевірку до `Reservation.overlaps`; перевірте перетин і суміжні інтервали. |
| **Creator** | `ReservationController` створює `Reservation`, обчислює ID та змінює колекцію бронювань. | Передайте створення об'єкту, який має потрібні дані та керує колекцією; не надавайте Controller прямий доступ до сховища. |
| **Controller** | Controller сам перевіряє всі правила, перебирає бронювання та приймає рішення про конфлікт. | Залиште йому приймання системної події та делегування сервісу. |
| **Low Coupling** | Сервіс бронювання напряму залежить від конкретної бази даних, поштового клієнта або UI. | Відокремте предметний сценарій від зовнішніх компонентів; додавайте порт лише для реальної межі зміни. |
| **High Cohesion** | Один `ReservationService` також форматує звіти, експортує CSV і надсилає сповіщення. | Згрупуйте разом відповідальності, що змінюються з однієї причини; винесіть звіт або сповіщення лише за наявності такої вимоги. |
| **Polymorphism** | У кількох методах ростуть однакові `if equipment.kind == ...` для різних правил обладнання. | Якщо типи справді мають різну поведінку, замініть розростання умов поліморфною політикою та порівняйте складність. |
| **Pure Fabrication** | `Reservation` одночасно зберігає часовий інтервал і формує CSV-звіт або надсилає email. | Розгляньте окремий об'єкт для звітування чи сповіщень; не додавайте його, якщо такої потреби немає. |
| **Indirection** | Доменний сервіс викликає конкретний API сховища або сповіщень у багатьох місцях. | За реальної потреби введіть вузький посередницький контракт, щоб ізолювати доменну логіку від провайдера. |
| **Protected Variations** | Кілька об'єктів залежать від полів і статусів конкретного провайдера сховища. | Знайдіть джерело очікуваних змін і локалізуйте адаптацію за стабільною межею. |
| **SRP** | Клас одночасно перевіряє запит, резервує обладнання, друкує повідомлення й керує зберіганням. | Вкажіть окремі причини для змін і розділіть тільки ті обов'язки, які справді змінюються незалежно. |
| **OCP** | Для кожного нового типу обладнання треба змінювати кілька умов у сервісі. | У TODO 6 додайте нове правило як політику без редагування основного сценарію. |
| **LSP** | Підклас політики посилює передумови або порушує обіцяний результат, через що його не можна підставити замість базової політики. | Сформулюйте контракт і перевірте кожну реалізацію однаковими контрактними тестами. Якщо це не підтип, використайте композицію замість успадкування. |
| **ISP** | Controller змушений залежати від великого інтерфейсу зі звітами, видаленням і налаштуванням сховища, хоча йому потрібен лише `reserve`. | Виділіть вузький `ReservationServicePort` і передайте Controller об'єкт лише з потрібною операцією. |
| **DIP** | Controller сам створює конкретний сервіс або сховище й не може працювати з іншою реалізацією без змін. | Передайте залежність ззовні через абстракцію; перевірте Controller тестовою реалізацією порту. |
| **KISS** | Для однієї in-memory колекції створено кілька фабрик, фасадів і шарів без окремих причин для змін. | Приберіть зайві рівні, залиште найпростішу структуру, яка виконує вимоги, і повторно запустіть поведінкові тести. |
| **DRY** | Controller і Service незалежно реалізують однакову перевірку інтервалу, тож правила можуть розійтися. | Залиште одне авторитетне місце перевірки; інші компоненти делегують йому, а тести підтверджують межові випадки. |
| **YAGNI** | Додані скасування, email-сповіщення, ролі користувачів або збереження в БД до появи відповідної вимоги. | Видаліть невикористану функціональність і залежності; залиште реалізацію для наявних вимог лабораторної. |
| **Law of Demeter (Закон Деметри, LoD)** | Controller читає внутрішній ланцюжок на кшталт `service.repository.reservations[0]`, щоб отримати дані. | Попросіть безпосередній collaborator виконати потрібну операцію або повернути потрібний результат; не додавайте accessor, якщо сценарій цього не вимагає. |

Один фрагмент може ілюструвати кілька принципів, але студент має пояснити різницю: GRASP підказує призначення відповідальності, а SOLID — якість меж, розширення та залежностей.

7. Після кожного кроку запускайте відповідні тести. Наприкінці запустіть весь набір і перевірте, що немає помилок або пропущених студентських тестів.
